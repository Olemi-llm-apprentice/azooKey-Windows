# azooKey-Windows 技術選定理由書

## 1. 概要

本ドキュメントでは、azooKey-Windowsで採用した技術・ライブラリ・設計パターンの選定理由を説明します。

---

## 2. プログラミング言語

### 2.1 Rust (IMEクライアント、UIプロセス、サーバー)

**選定理由**:

| 観点 | 理由 |
|------|------|
| メモリ安全性 | IMEはすべてのアプリケーションに影響するため、メモリリークやクラッシュは致命的。Rustの所有権システムにより安全性を担保。 |
| Windows API | `windows-rs`クレートによる型安全なWindows API呼び出し。COMインターフェースも安全に利用可能。 |
| パフォーマンス | ネイティブコードにコンパイルされ、GCによる遅延なし。キー入力のレイテンシに敏感なIMEに最適。 |
| エコシステム | `tonic` (gRPC)、`wry` (WebView)、`tao` (ウィンドウ) など成熟したクレートが利用可能。 |

**代替案の検討**:

| 言語 | 不採用理由 |
|------|-----------|
| C++ | メモリ安全性の担保が困難。Windows APIの利用は可能だがボイラープレートが多い。 |
| C# | .NET依存、IME DLLとしての配布に課題。 |
| Go | Windows COM操作のサポートが限定的。 |

### 2.2 Swift (変換エンジン)

**選定理由**:

| 観点 | 理由 |
|------|------|
| 互換性 | AzooKeyKanaKanjiConverterがSwiftで実装されており、再実装なしで利用可能。 |
| Swift for Windows | Swiftの公式Windows対応により、ソースコード互換でのビルドが可能。 |
| 変換ロジック | 複雑なかな漢字変換ロジックをそのまま流用できる。 |

**代替案の検討**:

| アプローチ | 不採用理由 |
|-----------|-----------|
| Rustで再実装 | 変換エンジンは非常に複雑で、再実装コストが膨大。バグの混入リスクも高い。 |
| WASM化 | Swift→WASMの変換パイプラインが成熟していない。パフォーマンス懸念。 |

### 2.3 TypeScript + React (設定アプリ)

**選定理由**:

| 観点 | 理由 |
|------|------|
| 開発効率 | 型安全なJavaScript。UIの迅速な開発が可能。 |
| Tauri連携 | Tauriが公式にReactをサポート。 |
| UIライブラリ | shadcn/uiによるモダンなUIコンポーネント。 |

## 3. フレームワーク・ライブラリ

### 3.1 Text Services Framework (TSF)

**選定理由**:

| 観点 | 理由 |
|------|------|
| 標準API | Windows標準のIMEフレームワーク。すべてのアプリケーションと互換性がある。 |
| 機能性 | 候補ウィンドウ、言語バー、入力モード管理など必要な機能が揃っている。 |
| 将来性 | Windows 10/11で継続サポートされている。 |

**参考実装**:
- khiin-rs (台湾語IME、Rust実装)
- Google Mozc (日本語IME、C++実装)
- Microsoft TSFサンプル

### 3.2 gRPC + Protocol Buffers

**選定理由**:

| 観点 | 理由 |
|------|------|
| 効率性 | バイナリプロトコルによる高速な通信。JSONより小さいペイロード。 |
| 型安全性 | .protoファイルから型が自動生成される。 |
| 言語間通信 | Rust (tonic) と Swift 間の通信に適している。 |
| ストリーミング | 将来的なリアルタイム通信拡張に対応可能。 |

**代替案の検討**:

| 技術 | 不採用理由 |
|------|-----------|
| REST/JSON | オーバーヘッドが大きい。型安全性が低い。 |
| Named Pipe | プロトコルを自前実装する必要がある。 |
| Shared Memory | 複雑性が高い。プロセス間同期が困難。 |

### 3.3 WebView (wry) - 候補ウィンドウUI

**選定理由**:

| 観点 | 理由 |
|------|------|
| 柔軟性 | HTML/CSS/JavaScriptによる自由度の高いUI設計。 |
| ダークモード | CSSメディアクエリで簡単に対応可能。 |
| 開発効率 | Web技術者でも貢献可能。 |
| 実績 | Tauriで使用されており、安定性が検証済み。 |

**代替案の検討**:

| 技術 | 不採用理由 |
|------|-----------|
| Win32 GDI | 開発コストが高い。柔軟性が低い。 |
| WPF | .NET依存。DLLサイズが大きくなる。 |
| Qt | ライセンス問題。依存が大きい。 |

### 3.4 Tauri (設定アプリ)

**選定理由**:

| 観点 | 理由 |
|------|------|
| 軽量 | Electronと比較して非常に小さいバイナリサイズ。 |
| Rust連携 | バックエンドがRustで、他コンポーネントとの一貫性がある。 |
| セキュリティ | サンドボックス化されたWebViewを使用。 |

### 3.5 llama.cpp (Zenzai推論)

**選定理由**:

| 観点 | 理由 |
|------|------|
| クロスプラットフォーム | CPU/CUDA/Vulkan/Metal対応。 |
| GGUF形式 | 量子化モデルの標準形式。モデルサイズを大幅に削減可能。 |
| パフォーマンス | 高度に最適化された推論実装。 |
| 活発な開発 | オープンソースで活発にメンテナンスされている。 |

## 4. 設計パターン

### 4.1 マルチプロセスアーキテクチャ

**選定理由**:

| 観点 | 理由 |
|------|------|
| 分離 | IME DLL、変換エンジン、UIを分離することで、クラッシュ時の影響を局所化。 |
| 言語混在 | Rust DLLとSwift DLLを別プロセスで実行することで、ランタイム競合を回避。 |
| 更新 | コンポーネント単位での更新が可能。 |

**トレードオフ**:
- プロセス間通信のオーバーヘッド
- 起動時間の増加
- メモリ使用量の増加

### 4.2 状態機械 (Composition State)

**選定理由**:

| 状態 | 説明 |
|------|------|
| None | 入力なし |
| Composing | 入力中（ライブ変換表示） |
| Previewing | 候補選択中 |
| Selecting | 候補リスト操作中 |

明確な状態遷移により、複雑なキー入力処理を整理。

### 4.3 FFI (Foreign Function Interface)

**Rust ↔ Swift 間通信**:

```
Rust (gRPC Server)
       │
       │ FFI Call
       ▼
Swift (azookey-server.dll)
       │
       │ Swift Package
       ▼
AzooKeyKanaKanjiConverter
```

**命名規則**: `@_silgen_name` でC互換関数名を指定

```swift
@_silgen_name("AppendText")
@MainActor public func append_text(
    input: UnsafePointer<CChar>,
    cursorPtr: UnsafeMutablePointer<Int>
) -> UnsafeMutablePointer<CChar>
```

## 6. 今後の技術的課題

### 6.1 パフォーマンス最適化

- gRPC通信の遅延削減
- 変換エンジンの初期化時間短縮
- メモリ使用量の削減

### 6.2 安定性向上

- IME DLLのクラッシュ耐性向上
- プロセス間通信のリトライ機構
- グレースフルシャットダウン

### 6.3 機能拡張のための基盤

- プラグインアーキテクチャの検討
- 辞書フォーマットの標準化
- 設定の同期機能
